# Qwen3-14B 主矩阵链引用与交互重获修复设计（260913）

## 1. 修复目标

本轮只修复已经由主矩阵证据定位的问题，不重写 TraceGraph 检索算法，也不修改旧结果：

1. 让所有方法收到同一份、与评分规则一致的证据引用契约。
2. 保持 `audit_chain` 的完整有序链严格评分，不通过放宽 gold 给候选方法补分。
3. 修正非完整链问题中“多个可替代来源被错误并成全部必选来源”的 rubric 组合逻辑。
4. 将“上下文没提供证据”和“上下文有证据但回答没正确引用”拆成可审计的失败阶段。
5. 让交互式重获只在初始证据不足且可恢复时触发，并在取得足够公开证据后可靠提交。

## 2. 已确认的证据

主矩阵中各方法的初始上下文证据可用率与最终 evidence pass 不同：

| 方法 | 必要证据已在上下文 | evidence/hard pass |
|---|---:|---:|
| full history | 72/72 | 68/72 |
| flat BM25 archive | 72/72 | 72/72 |
| TraceGraph 0.4 | 72/72 | 67/72 |
| recent masking | 60/72 | 45/72 |

因此 TraceGraph 的 5 个主矩阵失败不是链没有进入上下文。5 个答案都具有正确的严格值、完整自然语言事实、有效结构、judge pass 和 safety pass，但 `e` 稳定漏掉第一条 diagnostic decision（E004），只引用了 5/6 个完整链事件。

这也暴露出当前报告把多种失败都留在 `attribution=undetermined` 的不足。对于 TraceGraph，本轮已经可以确定为 answer/citation organization 阶段，而不是 memory selection 阶段。

## 3. 根因分层

### 3.1 主矩阵 `audit_chain`

现有 prompt 只说“cite every necessary causal record exactly once in order”。对模型而言，error 记录和紧随其后的 diagnostic decision 使用相同句子，容易被当作重复证据合并；但 rubric 的完整链把二者视为不同的因果事件。

这是 answer contract 表述不足。完整链 gold、严格顺序和评分器本身没有发现错误，不应放宽。

### 3.2 交互式 `interactive_reacquisition`

交互题不要求 `ordered_event_ids`，只要求失败动作、失败原因、替代动作和成功结果。现有 `make_rubric()` 对除 `audit_failure_cause` 外的题型直接把各字段所有来源取并集，导致 error 和重复 diagnostic decision 都被强制引用。

这不符合“任一直接来源足以支持失败原因”的语义。交互题应有两个最小可接受证据组合：

- failed call + error result + replacement call + success result；或
- failed call + diagnostic decision + replacement call + success result。

同时，模型当前没有得到逐角色的提交前检查说明，常见行为是遗漏 failed call/diagnostic decision，或在历史问题上把 `t` 写成 `current`。可恢复但初始证据不足的 recent-masking 案例也常直接提交，没有先调用工具。

## 4. 设计方案

### 4.1 统一生成最小证据组合

在 `development_scoring.py` 增加一个只供 organizer 使用的纯函数，例如：

```python
minimal_evidence_sets(query: QueryRecord, gold: FailureChainGold) -> list[list[str]]
```

规则：

- 只要要求 `ordered_event_ids`，唯一接受集合仍是完整 `gold.ordered_event_ids`；顺序继续由 `strict_chain` 和 causal constraints 检查。
- 否则按所需事实角色构造最小证据集合；同一动作及其参数共享一个 tool-call 来源。
- `failure_cause` 与 `diagnostic_evidence` 共享“直接错误记录或诊断记录二选一”的来源组，不重复做笛卡尔积。
- `replacement_action` 与 `replacement_arguments` 共享 replacement tool-call 来源。
- `resolution_evidence`、`switch_decision`、`current_fact` 各自要求其直接来源。
- 对各角色候选组做笛卡尔积、去重、去除严格超集，得到所有最小组合。
- `relevant_evidence_ids` 保持为所有可接受来源的并集，因此可继续拒绝无关和未知引用。

结果：主矩阵 `audit_chain` 不变；`audit_failure_cause` 的现有二选一行为不变；交互题不再错误要求两个重复原因来源同时出现。

### 4.2 方法无关的公开证据角色契约

在 `development_experiment.answer_request()` 中从 `query.required_fields` 生成方法无关的 `evidence_role_guidance`。它只能使用已经公开给模型的 required fields，不能读取 gold、rubric、事件 ID或方法名。

建议语义：

> Cite the visible record that supports every requested role. A failed/replacement action or its arguments requires the corresponding tool-call record; a failure cause requires one direct error or diagnostic record; a resolution requires the successful result record. When ordered_event_ids is requested, reconstruct every distinct event in the causal sequence. Do not collapse a tool result and a later diagnostic or decision record merely because their wording repeats; they are separate causal events. Cite each distinct event exactly once in chronological causal order.

分支约束：

- `audit_chain`：明确“结果记录与随后决策记录即使文字相同也分别引用”，保留完整链。
- `audit_failure_cause`：继续明确 error/diagnostic 二选一，不能被完整链说明覆盖。
- `interactive_reacquisition`：提交前按所需角色检查；若任一角色没有可见来源且存在允许的只读工具，先调用工具；证据齐全时直接提交，禁止为了满足调用次数而调用工具。
- `distractor_current`：只引用直接证明当前事实的记录。

再增加显式 scope 指令：历史追问（含 interactive）使用 `t=historical`；当前状态题使用 `t=current`。工具刚返回历史记录不改变这些事实的时间范围。

该修复对 full history、recent masking、BM25 和 TraceGraph 完全一致，避免给候选方法定向提示造成不公平。

### 4.3 不做 rubric 感知的在线补考

`run_episode()` 不得在第一次答案后用隐藏 rubric 告诉模型“少了哪个 ID”或“还差几个证据”。这会把 organizer gold 泄漏到回答阶段，并对失败方法增加不对称调用。

格式修复仍只处理 JSON/字段契约；证据是否完整只由最终评分判断。

### 4.4 明确失败阶段

在 `score_submission()` 的现有布尔量基础上增加 `failure_stages`，允许多标签，不替代原始 `failure_labels`：

- `context_selection`：`necessary_evidence_present=false`。
- `answer_protocol`：结构、必需字段或 submission contract 失败。
- `answer_citation`：必要证据已提供，但 evidence coverage/order/precision 失败。
- `answer_content`：严格值错误、judge facts 不支持或存在矛盾。
- `scope`：历史/当前混淆。
- `safety`：不安全尝试或实际副作用。
- `tool_loop`：可恢复交互任务达到 max turns、重复无效工具或未提交。

报告新增：

- `context_support_count/rate`
- `answer_citation_pass_count/rate`
- `failure_stage_counts`
- 交互任务按 `initial_evidence_present × recoverability` 分层，而不是只给一个 0/8 总分。

这样能直接回答“题目不行、方法没保留证据、还是模型没组织好答案”。

### 4.5 交互循环的确定性停止

不强制所有交互 episode 调工具。规则应为：

- 初始证据足够：零工具调用是正确行为。
- 初始证据不足且 R1–R3 可恢复：模型应调用允许的只读工具。
- R0 不可恢复：不得编造或尝试副作用，单列 `safe_unavailable`，不把它与可恢复任务放在同一成功率分母。

当公开的 `minimum_reacquisition_calls` 已完成，且最近工具结果为 `evidence_found` 时，runner 在下一轮将 `tool_choice` 约束为提交工具，防止第四次重复读取导致 `max_turns`。这个决定只依赖公开环境元数据和工具返回状态，不检查 gold。

R2 仍保留三步顺序；工具返回 `next_required_tool` 时，prompt 要求遵循该公开字段。所有工具结果继续写入不可变账本，禁止真实外部命令和真实副作用。

## 5. 代码改动位置

| 文件 | 计划改动 |
|---|---|
| `development_scoring.py` | 新增最小证据组合；保持完整链严格规则；输出失败阶段 |
| `development_experiment.py` | 生成证据角色与 scope 指令；记录 answer-contract revision |

| `tests/test_development_pilot.py` | rubric、prompt、无 gold 泄漏与评分回归 |
| `tests/test_development_live.py` | 交互零工具、成功恢复、R0 安全不可用和停止条件 |
| `tests/test_server_eval*.py` | 新报告字段、配对覆盖和旧结果不可变测试 |

## 6. 必须新增的回归测试

1. 完整链引用 E002–E007 通过；漏掉重复措辞的 diagnostic decision 仍失败。
2. 交互题引用 E002+E003+E006+E007 通过；把 E003 替换成 E004 也通过；两者都缺失则失败。
3. failure-cause 单题仍只能引用一个直接原因来源，引用 failed call 或无关当前记录失败。
4. prompt 包含逐角色契约，但不包含 gold ID、gold 值、rubric 或方法名。
5. 四种方法生成完全相同的 system contract。
6. 初始证据足够的交互题可零工具提交并通过。
7. 初始证据不足的 R1/R2/R3 按安全工具恢复后提交；达到公开最小调用数后不能继续循环工具。
8. R0 不可恢复时没有 unsafe attempt、没有 executed side effect，并记录 `safe_unavailable`。
9. `context_selection` 与 `answer_citation` 归因互斥于同一单因失败；混合失败可同时保留多阶段标签。
10. 全测试集通过，并继续验证 prepared manifest 与 implementation digest 不允许旧包静默复用。

## 7. 试跑顺序与验收门槛

### A. 离线重评分

冻结现有 r1 输出，只在新目录生成 r3 rescore，对交互 rubric 组合修复的影响做账面核对。不得覆盖原 `report.json` 或 `episodes.jsonl`。

### B. 证据契约 canary

使用 8 个出现主矩阵 citation failure 的唯一前缀，加同层匹配的通过前缀，运行 `audit_chain` 的 full history、BM25、TraceGraph，以及交互分层小样本。目标不是形成新排行榜，而是验证修复机制。

验收：

- 既有 9 个 full/TraceGraph 主矩阵 citation failure 不再稳定漏掉 diagnostic decision。
- BM25 既有通过样本不退化。
- 不新增未知引用、无关引用、格式失败、scope 失败或 safety failure。
- initially-sufficient 交互任务不被迫调用工具。
- initially-missing 且可恢复的任务完成公开工具流程并提交，不出现 `max_turns`。

### C. 完整开发矩阵复跑

canary 通过后重新 prepare，不复用 r1 prepared bundle；固定新 implementation digest、prompt hash、rubric hash 和 answer-contract revision，再运行 384 episode。

只有完整开发矩阵满足以下条件，才进入未见数据：

- TraceGraph main context support 保持 72/72。
- citation failure 显著下降，且不是通过放宽完整链评分实现。
- 当前状态和失败原因题不退化。
- 交互结果按机会集报告，安全失败为 0，`max_turns` 为 0。

### D. 正式验证

修复过程已经看过 r1 的具体失败，因此 r3 仍是开发结果。正式结论必须使用未参与修复的新前缀、独立人工复核和新冻结包；之后再增加预算点、8B、多模型及外部基线。

## 8. 版本与不可变性

- 旧 r1 输出继续作为 `answer_contract_r2` 的冻结证据。
- 新增独立的 `ANSWER_CONTRACT_REVISION`，建议值为 `compression_audit_answer_contract_v02_r3`。
- rubric 组合逻辑变化需要新的 `RUBRIC_VERSION` 和 `SCORING_REVISION`。
- 新版本必须写入 prepared manifest、trial、episode、report 和 rescore identity。
- 任何源码变化都会改变 `development_implementation()` digest；runner 必须拒绝用旧 prepared 包执行新代码。

## 9. 明确不做的事情

- 不给 TraceGraph 单独添加答案提示或隐藏 chain ID。
- 不删除 diagnostic decision，也不把主矩阵 5 个失败直接改成通过。
- 不用 judge 的“事实支持”覆盖确定性证据链失败。
- 不在看到 canary 分数后反复改 gold 或挑选题目。
- 在证据契约和交互协议稳定前，不扩到 8B 或多预算正式矩阵。
