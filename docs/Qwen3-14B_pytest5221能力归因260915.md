# Qwen3-14B `pytest-5221` 能力归因实验（260915）

## 结论

在已经暴露的短题 `pytest-dev__pytest-5221` 上，Qwen3-14B 即使启用真实 thinking、
使用未压缩 Full History、将步数上限从 12 提高到 40，并采用权重 README 推荐的
thinking sampling，仍未通过隐藏测试。

最终有效运行在第 21 次模型调用主动提交，未耗尽 40 步；但模型没有产生任何有效源码 diff，
没有运行测试，也没有检查最终 diff。它执行的长 `sed` 命令所有匹配均未命中，却把“命令返回
0”误判为“功能已实现”，随后提交。隐藏 `FAIL_TO_PASS` 的两个测试均失败。

因此，这条题的 0 分不能解释为题目或评测器无效，也不能归因于 12 步上限、thinking 关闭或
历史压缩。直接失败点是当前冻结 Qwen3-14B + mini-SWE-agent 脚手架下的源码定位、有效编辑、
测试验证和基于观测纠错能力。这个结论不等价于“Qwen3-14B 在所有代码代理脚手架中都无法
解决该题”。

本实验是开发期能力归因，不是官方 SWE-bench 分数，也不是独立验证。

## thinking 与动作协议验证

151 上的 vLLM 0.8.5 只有 DeepSeek-R1 和 Granite reasoning parser，没有 Qwen3 parser，因而
没有错误套用其他模型的 parser。请求使用 Qwen3 chat template 的 `enable_thinking=true`，
并通过 vLLM 已启用的 Hermes 原生工具解析器返回单一 `bash` 调用。

协议探针显示：

1. 自由响应会产生非空 `<think>...</think>`，证明 thinking 实际开启。
2. 强制 JSON schema 会抑制 `<think>`，不适合作为能力归因。
3. `tool_choice=auto` 可在同一响应中同时保留完整 `<think>` 和解析后的单一 `bash` 调用。

最终有效运行的 21 个 provider 请求全部有效；20 个工具调用响应均有完整非空 thinking。
另有 1 次 thinking 用满 2048 completion token 而未完成工具调用，随后通过 1 次
`mini_format_repair` 恢复。

## 能力归因与影响

1. **不是题目无效。** 同一 pinned 镜像上，原始提交在两个 `FAIL_TO_PASS` 测试失败，应用数据集
   gold patch 后通过。
2. **不是历史不足。** 最终请求保留全部 40 个事件，历史 18,810 token，超过要求的 8192，
   且总 prompt 19,646 低于 32,768 context window。
3. **不是 12 步过早截断。** 上限已提高到 40，但模型在第 21 次调用自行提交。
4. **不是 thinking 未生效。** 原始 provider 响应证明每个成功工具动作前都有非空 thinking。
5. **不是动作传输完全失效。** 21/21 请求有效，模型完成 20 次原生工具调用并走通提交路径。
6. **当前直接瓶颈是代理能力。** 模型没有把搜索结果收敛到正确输出函数，没有验证编辑是否命中，
   也没有执行提示明确要求的测试与 diff 检查。

这使 `pytest-5221` 从“短题也为 0”升级为更有力的能力归因证据，但单题仍不能估计模型总体
SWE-bench 成功率。

## 下一步

1. 继续停止剩余 5 道未暴露题；当前模型尚未满足主矩阵的代理可行性门槛。
2. 若研究目标是比较记忆方法，现在可以合理考虑更强、代码专用的模型。先只在已经暴露的
   `pytest-5221` 上做 smoke test，要求同时满足：非空源码 diff、模型实际运行测试、隐藏测试通过。
3. 更强模型通过后，再从 5 道保护题中只释放 1 道新 canary；不要一次暴露全部。
4. 若暂不更换模型，只能把下一轮明确标为“代理脚手架干预实验”，例如重复命令阻断、空 diff
   禁止提交、测试前禁止提交。这类改动不能当作 TraceGraph 记忆方法收益。
5. 在出现至少一条成功或可纠错轨迹前，不启动 TraceGraph 与其他记忆方法的主矩阵。
