# Qwen3-14B Track A 统一六方法 1024 预算开发矩阵（2026-09-18）

## 结论

统一开发矩阵已经完整运行。六种方法在同一个 Qwen3-14B、同一个冻结 Harness、同一组 8 个受控开发前缀、同一 1024-token history budget 和同一多分数评分协议下比较。208/208 个计划 episode 完成，共发出 626 次 provider 请求，`stop_reason=null`。

本次没有 `integration_invalid`。因此，旧 canary 中由 AMA 适配错误或裁判输出协议错误造成的“全零/全失败”现象已经排除；当前 AMA 和 Rolling Summary 的零分项来自正确配置下的真实方法构建失败，按预注册规则进入能力分母并计 0。

但这仍是暴露开发集上的 Track A 工程比较，不是独立测试，也不能直接作为论文最终主结果。当前受控题对 Full History、TraceGraph 和词法 BM25 已接近或达到天花板，尚不能证明 TraceGraph 的图结构本身优于强词法检索。

## 运行有效性与失败归因

- 全部 208 个 episode：185 `valid`、23 `method_failure`、0 `integration_invalid`。
- 主实验 144 个 episode：129 `valid`、15 `method_failure`、0 `integration_invalid`。
- AMA：4/8 个前缀的共享 memory construction 达到输出上限，导致对应 12 个主问题无法进入有效答题。它们是正确配置下的方法资源/协议失败，不能删掉，也不能再标成 Harness 集成无效。
- Rolling Summary：1/8 个前缀的共享构建达到输出上限，导致对应 3 个主问题失败。
- 另外 8 个 `method_failure` 全部来自不进入六方法排名的 `irrelevant` 诊断控制，其答案在一次格式修复后仍违反答案协议。
- 裁判格式修复触发 5 次，5 次均得到合法 verdict；首次错误及两次请求均已入账。没有方法因为裁判 JSON 格式错误而被记 0。

## 科学解释

1. TraceGraph 在本次开发题上达到 Full History 的 100 分，同时主实验部署 token 比 Full History 少约 82.6%。这支持“在这些题上能以更短上下文完整保留失败链”的工程结论。
2. Flat BM25 同样达到 99.96，总分只因一个问题的溯源不完整而略低；TraceGraph 的 token 比 BM25 少约 31.2%，严格审计多通过 1 题。这个差距不足以单独证明因果图机制优于词法检索。
3. ACON 的语义因果分为 90.28，但溯源为 0、严格审计为 0/24。多分数体系因此没有把“语义上大致正确但无法绑定来源”粗暴地全部记 0，也没有把它误写成完整可审计记忆。
4. AMA 与 Rolling Summary 的低分混合了记忆质量和构建可靠性。论文必须同时报告分项、有效运行率和失败原因，不能只报总分。
5. 这组 8 个开发前缀已参与评分与适配修复，且对 BM25 近乎饱和。下一步若要支撑论文主张，必须冻结更难且未暴露的独立 test prefixes，并完成 BM25 failure-episode unit、去因果边、去 pair closure、随机边等结构消融，以及 native/canonical Harness 交叉验证。
