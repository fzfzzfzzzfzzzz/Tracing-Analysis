## 修复内容

1. 裁判的 contradictions 必须是 `answer.a` 的逐字子串；未知抽取字段、无法核验的 span 和不唯一 quote 不再被静默接受。
2. 旧裁判使用的 `text` 字段只在 offset 能独立复原原文时作为兼容别名；唯一 quote 的错误 offset 可以确定性修正，并记录 warning。
3. 无效裁判输出标为 `judge_protocol_failure` 与 `semantic_pending_review`，不再归罪为 `semantic_failure`。
4. 裁判请求移除了容易诱发照抄的候选矛盾；危险误判按完整评分栈是否错误放行计算。
5. 答案请求公开必需的精确标签名，并按题型给格式说明；当前状态题不再看到历史字段示例。缺失精确标签会得到一次独立计费的格式修复回合。
6. vLLM 0.8.5 的 llguidance 对 `uniqueItems` 报未实现并直接生成 EOS。服务器适配层只从 wire schema 删除该关键词；本地解析器仍检查列表唯一性、非空字符串、精确键集合、enum 和 boolean，所以逻辑协议没有放宽。修复前 40/40 答案为空；修复后 40/40 最终结构有效。
7. failure-cause 中 E003 错误记录与 E004 决策记录包含完全相同的诊断文本，改为任选其一即可满足证据覆盖；chain 仍要求完整有序链。
8. suite 准备阶段对 104 个 rubric 执行 organizer canonical answer 自检；离线复算写入源/结果/评分代码哈希，并确认新 provider 请求为 0。

## 旧 0/48 的重新归因

旧主轨每种方法有 48 道历史题。Full history、BM25 和 TraceGraph 的必要证据实际为 48/48 可见，Recent masking 为 24/48；结构化输出四种方法均为 48/48。与此同时，旧裁判在四种方法上均有 48/48 条“矛盾”不属于答案原文。因此四组 0/48 至少同时混合了答案精确标签缺失、裁判越界、语义待复核，以及 Recent 的部分检索缺失，不能据此比较记忆算法或断言模型没有能力。

对旧 384 条输出作零新请求复算后：`semantic_failure` 从 275 降到 6，`semantic_pending_review` 从 5 升到 325，新增 320 条 `judge_protocol_failure`；hard pass 仍为 103，audit pass 从旧口径 103 调整为 53。这个变化不是把失败改成成功，而是把无证据的负面判决恢复为待复核。

以后遇到“全是 0”时，按以下顺序判断：先看 canonical rubric 自检，再看 Full/Oracle 的最终结构与 hard pass，再看必要证据是否可见，最后才看已通过真实答案迁移校准的语义裁判。Full 与 Oracle 的 hard pass 都低，才优先怀疑任务/协议或基础模型；只有压缩方法低而 Full/Oracle 高，才归因检索/记忆方法；hard 高而 audit 低且 judge protocol failure 高，应归因裁判。
