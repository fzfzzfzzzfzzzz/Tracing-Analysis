## 第四阶段的记录整理办法 R0–R4 冻结顺序（当前主线）

本节取代旧文档中“P4 只可运行 ACON+Card”的行动顺序，但不改写任何历史结果。正式参数见 [第四阶段的记录整理办法 实验开始前定下的规则](第四阶段_实验开始前定下的规则.md)；结果只登记在 [第四阶段的记录整理办法 结果账本](第四阶段新方案做了什么和得到什么.md)。

1. **R0 治理与成本审计**：冻结旧 第一阶段–4 文件指纹，复现 192-view graph/closure 成本错位，并证明至少一个候选子集有 ≥30% 模型服务商-token oracle headroom。失败即停止。
2. **R1 状态层**：验证纯 tool-call assistant 也生成 Decision、同 截至当时已有的记录 重建 文件指纹 稳定、未来 suffix 不影响 截至当时已有的记录，且所有 reducer 从 neutral 判断记录现在是否还需要 只读 cutoff 内事件。
3. **R2 多表示机制**：运行 E1/E4 与 `[2048,4096,8192,12288,16384]` 真正拼成完整请求后的-budget sweep。主预算是达到 hard coverage 100% 且 conservative fallback ≤5% 的最小预算；同时必须通过结构等价、decision sufficiency 和 ≥30% median 真正拼成完整请求后的 marginal-cost 降幅继续或停止条件。
   - 实际 R2 为 停止 后执行零 API R2.1：冻结历史 文件指纹，对同一 261 点按真实 τ³/LiteLLM prompt 口径归因，并计算保留完整 policy/native schemas/hard state 时的可达性下界。结果 fixed-floor 最大 median 降幅为 `28.451% <30%`，故采用不可达分支，不实现 v1.1。
4. **E0 完整 eligibility**：每个域至少 10 tasks、median actions ≥10、dynamic-history ≥40%、headroom ≥30%、至少三类 判断记录现在是否还需要 现象各 ≥30 decision points、snapshot 可重放、Full success 在 20%–85%、native evaluator 能识别成功与副作用。任务仅按结构特征选择并以 task ID 稳定排序。
5. **R3 同一段已有记录 小规模试跑**：先运行 R4 Full 首 seed 的 20 sessions并复用为 eligibility/截至当时已有的记录 capture；E0 失败不进入 不同后续。通过后冻结 retail/airline 各 15 截至当时已有的记录，运行 `30 × 3 treatments × 2 replicates = 180` 个最多 3-action 的短分支。
6. **R4 development 组合实验**：仅在 R3 全部 继续或停止条件 通过后运行剩余矩阵。固定 10 retail + 10 airline tasks、2 seeds、4 conditions，共 160 sessions；前述 20 个 Full sessions计入总数。

R3/R4 temperature=0、并发=1，不自动补跑。R4 四条件固定为 保留全部旧记录的办法、文件指纹-必须保留 official ACON、第四阶段的记录整理办法-Core、official ACON + 第四阶段的记录整理办法 safety/state layer。agent、user simulator 和 ACON compressor 固定 `zai/glm-4.7-flash`，max steps=50、timeout=900 秒、run 间隔20秒。启动前必须重新核验免费价格；任何非零计费估算、额度不足、模型 fallback 或累计超过 340 个外部分支/会话均在调用前 拿不准时宁可保留或停止。

本轮只允许得出“τ³ retail/airline 跨域 development evidence”。第二 benchmark 和两位独立人工 事先规定的标准答案 不在本轮范围，不能因 τ³ 正向结果宣称最终 AAAI 证据链已完成。

当前执行已在 R2.1 与 E0 双重停止；R3/R4 列表保留为冻结协议，不是待自动执行任务。

## 历史通用协议

### 0. 环境与固定变量

正式比较中固定：benchmark task IDs、trial seeds、agent model、user model、工具集合、max steps、temperature 和并发度。唯一变化是 记录整理办法。每个条件使用相同 token budget；保留全部旧记录的办法 作为不受 budget 限制的性能上界。

先运行：

```powershell
./scripts/bootstrap.ps1
./scripts/run_smoke.ps1
```

## 1. 收集或导入 保留全部旧记录的办法

推荐先用 τ³ `retail` 与 `airline` 的固定小样本，每域 10–20 tasks、至少 3 trials。也可以先导入官方历史工具使用记录进行离线验证。

```powershell
python -m tracegraph import-tau `
  --input data\raw\tau3\run-name `
  --output data\processed\tau3-graphs `
  --archive artifacts\tau3-archive
```

导入后必须检查：

```powershell
Get-ChildItem data\processed\tau3-graphs\*.json | ForEach-Object {
  python -m tracegraph validate-trace $_.FullName
}
python -m tracegraph verify-archive artifacts\tau3-archive
```

## 2. 实验一：离线记录现在是否还需要现象

运行完整 suite 后读取 `lifecycle_analysis.json`。报告各状态频数、`created→active`、`unresolved_failure→resolved_failure`、`active→critical_evidence`、`observation→superseded` 等转移，并按 domain、task length、tool/error 类型分层。

人工抽样至少 100 个节点做双人标注，报告 Cohen's κ；自动推断只作为候选标签，不直接当 事先规定的标准答案。

## 3. 实验二：Oracle 压缩上界

`oracle_upper_bound.json` 只使用完整工具使用记录的 post-hoc 结构信息，保留所有硬保护节点。报告可安全移除 token 比例与结构可靠性。它是方向可行性的上界分析，不与在线方法混为一谈。

## 4. 实验三：在线 记录整理办法

离线的 `online_replay.jsonl` 在每个 step 只构造该截至当时已有的记录图，用来检查未来信息泄漏与 context 大小。正式 task success 必须用 [τ³ live agent](怎样接入公开测试任务.md) 重跑。

历史第二阶段实验使用 512、1024、2048、4096 等 active-context 预算。第三阶段先冻结一个可行总预算，`full_ours` 默认只给 失败原因和避免办法的简短记录 分配总预算的 12.5%；除非 P1 暴露 card 边界问题，不重新 sweep 整个 active-context budget。

## 5. 实验四：去掉一个功能再比较

完整条件：

- `ours_without_graph_edges`
- `ours_without_lifecycle_states`
- `ours_without_failure_retention`
- `ours_without_constraint_retention`
- `raw_hard_failure_retention`（第二阶段无界原始失败硬保留对照）
- `full_ours`

`full_ours` 是第三阶段的 compact-card 策略；测试保证原始失败、audit-required 写操作和通用 Active 状态不会重新进入无界 mandatory 集合，并保证 失败原因和避免办法的简短记录 不触发历史 tool-call/result 消息闭包。

## 6. 强 用来比较的办法

一键 runner 包含：

- `full_trajectory`
- `last_k`
- `token_length_pruning`
- `summary_only`
- `llm_only_pruning`
- `agentdiet_style`
- `acon_style`

默认的后三类/摘要类是透明标记的 deterministic proxy，用于管线验证。论文主结果必须把 scorer/summarizer 替换为指定模型或官方方法，并在 文件清单 中写明版本、prompt 和 commit。

AgentDiet/ACON/Agent-Omit 的官方实现可用性、接口差异和 τ³ 接入验收标准见 [强 用来比较的办法 官方实现审计](其他公开方法能不能公平比较.md)。实验 文件清单 会 按拿不准时宁可保留或停止的规则记录每个 记录整理办法的实现类型与主结果资格。

## 7. 统计

- τ 任务成功率：按同一批题反复抽样得到的估计范围 95% CI；多 trial 报官方组合估计 `Pass^k = mean_task[C(c_i,k)/C(n_i,k)]`，其中基础设施型中止不进入 `n_i`。
- token/cost/overhead：按相同 task+trial 做配对差异与 反复抽样得到的估计范围 CI。
- policy violation / repeated failure：McNemar 或配对 permutation test。
- 多预算、多 domain 比较做 多项比较校正。
- 预先冻结 exclusion rule：上游 infrastructure error 单独统计，不当 agent failure。

## 8. 阶段性判断

若真实小样本中 median trajectory 太短、Oracle compression ratio 低、记录现在是否还需要转移稀少，或强 LLM-only 在相同预算下结构指标与 完整办法 无显著差异，应按报告要求调整 benchmark 或缩小论文主张，而不是扩大 项目自己设计的测试 结果。

## 9. 当前 GLM 阶段状态

2026-07-16 已完成真实 API 连通、Function Call、mock 端到端成功以及两次 retail 单任务 保留全部旧记录的办法。第一次完成全部 5 个目标工具动作但 user 没有停止；第二次正常 `user_stop`，但 agent 选择了错误键盘 variant，官方 reward 仍为 0。两次结果都不得改写为 task success。详细配置、成本、失败分析与三图离线结构 小规模试跑 见 [GLM 小规模试跑](第一次真实模型试跑是怎样做的_2026-07-16.md)。

项目提供默认关闭的确定性 user-stop 协议 adapter；是否启用必须在所有条件中固定。`glm-4.7-flash` 已提供零成本可用路径，并通过模型适用性 继续或停止条件。免费端点可能瞬时限流，因此矩阵显式记录跨 run 冷却，infrastructure error 仍单独排除。

保留全部旧记录的办法 适用性 继续或停止条件 已冻结并完成 10 tasks × 3 trials；任务、seed、成本估算、执行 cap 和通过阈值见 [正式实验矩阵](正式实验安排和费用限制.md)。

历史 `glm-4.5-air` Stage 1 为 `12/30 = 0.40`。`glm-4.7-flash` 随后用同一 继续或停止条件 取得 `16/30 = 0.5333` 并通过全部条件。对 Stage 1 图执行 `content_estimate_v2` 重计量后，中位内容工具使用记录为 4,875 tokens，继续或停止条件 仍通过；预算 sweep 推荐 4096。旧 120-session 同题比较 组合实验 的 reward/termination 保留为诊断，但其压缩条件受旧 token 口径影响，不能进入正式效果结论。替代的 corrected smoke、`g47f_ml_c2` 和 failure-rich `g47f_fr_c2` 使用冻结的 4096 预算，并同时报告估算 context tokens 与真实 agent 模型服务商 input usage。详细边界见 [Token 计量修正](模型输入量怎样计算和修正.md) 和 [GLM-4.7-Flash 结果](真实模型记录分类实验结果_2026-07-17.md)。

## 10. 第三阶段执行顺序

第三阶段按 `P1 → P2 → P3 → P4 Go/No-Go` 执行。P1 已完成 32 tasks × 4 conditions 的确定性机制实验；P2 已完成 Codex 临时 A/B，但正式 human 继续或停止条件 保持 拿不准时宁可保留或停止。P3 原始矩阵暴露 NL evaluator 配额造成的顺序偏差后，对受影响任务四条件平衡补跑，并形成 60-session、0-infra 的 task-stratified 修复后复合分析。最新 P4 继续或停止条件 因 human construct、Raw 双 token CI、Remove 机制 CI 和 success non-inferiority 四项 blocker 判为 停止，因此不执行 P4 扩展。当前结果和命令见 [第三阶段执行结果](第三阶段做了什么和得到什么.md)。
