# 工具调用历史压缩研究：实验进展与当前卡点报告

> 报告对象：未直接参与本项目的导师  
> 报告日期：2026 年 8 月 1 日  
> 当前阶段：Phase 5.1 已完成，项目处于停止并等待方向决策的状态

## 一、先说结论

本项目研究的是：当大语言模型连续调用多个工具时，能否只保留“接下来仍然有用”的历史记录，
删除已经完成、被替代或已经失效的记录，从而减少模型每一步需要重复阅读的内容。

目前得到的结论可以概括为：

1. 我们已经实现了一套比较可靠的“工具调用历史管理系统”。它能够保存完整原始记录、恢复被移出
   当前上下文的内容，并避免删除政策要求、用户确认和不可逆操作回执等关键证据。
2. 系统的安全性和可复现性测试表现良好。在 261 个历史决策点上，确定性、未来信息隔离、消息
   协议正确性和请求哈希检查均为 100%，没有发现关键证据被错误删除。
3. 但是，它目前不能在大多数场景下降低模型的完整输入成本。Phase 5 中只有 4/185 个合格决策点
   真正减少了输入；加入更丰富但仍然安全的本地规则后，提高到 10/185。
4. 即使采用一个故意偏乐观、不能实际发送给模型的上限估计，也只有 36/185 个决策点能够减少输入，
   仍远低于改变总体中位数所需的 93 个。
5. 因此，当前卡点不是程序无法继续优化，而是历史数据没有记录足够多的“某条信息何时已经失效或
   被消费”的事实。继续在旧数据上增加正则规则，预计无法解决这个问题，而且可能带来错误删除。

所以，当前实验没有证明该算法能够稳定节省模型输入，也没有进入外部模型效果实验。它证明的是：
系统可以安全工作，结构化关系记录确实有帮助，但现有轨迹提供的关系信息不足以支撑预期的成本收益。

## 二、这个研究具体在解决什么问题

一个能够调用工具的智能体，可能依次执行：查用户、查订单、修改订单、再次确认订单、退款等操作。
每次让模型决定下一步时，通常会把前面所有对话和工具结果重新放进输入。

这会产生两个问题：

- 历史越长，输入越贵、越慢；
- 很多旧结果已经过时，继续展示可能干扰模型判断。

可以把它类比成医生看一份持续增长的病历。完整病历必须保留以备审计，但医生做当前决定时，不一定
需要反复阅读每一次已经被后续检查替代的旧结果。理想系统应该同时维护两层记录：

- **完整档案层**：任何原始记录都不能丢失，需要时可以恢复；
- **当前工作层**：只向模型展示对下一步仍然有用的内容。

困难在于，系统必须有充分证据才能判断某条记录已经“没有用了”。如果判断过于激进，可能删除政策、
确认状态、失败原因或不可逆操作的回执，导致模型做出错误决定。

## 三、项目经历了哪些阶段

### 3.1 Phase 4：尝试把历史整理成更紧凑的决策状态

Phase 4 的主要思路是，不再把全部原始历史直接交给模型，而是把它们整理成一个结构化的“当前决策
状态”，包括当前目标、已知信息、待确认事项、政策约束和失败记录等。

工程上，这个阶段完成了状态图、提示词编译、完整请求成本计量、归档恢复和安全检查等基础设施。
但是成本实验没有达到预先规定的标准：

- 预期要求完整序列化输入的中位降幅至少为 30%；
- 实际离线降幅为 14.956%；
- 按真实运行请求口径重新计算后为 15.723%；
- 即使只考虑无法删除的固定政策和工具定义，理论最大中位降幅也只有 28.451%。

这说明在当时冻结的输入格式和成本定义下，30% 目标本身不可达到。因此 Phase 4 的 R2 被判定为
No-Go，即“没有达到继续外部实验的条件”。这个结果和原来的 30% 标准均被完整保留，没有事后降低
门槛。

### 3.2 Phase 5：改为只删除能够证明已经结束的工具记录

Phase 5 没有继续追求更复杂的摘要，而是采用更容易验证的办法：

> 原始内容不改写；只有当一整段工具调用能够被确定性证明已经完成、被替代或被解决时，才把它从
> 当前输入中移走。

这套方法称为 LiveSubgraph + GDSC-Prune。LiveSubgraph 可以理解为“当前仍然活跃的历史子图”，
GDSC-Prune 则只发送这个子图所对应的原始消息。

Phase 5 使用了全部 261 个冻结决策点，来自 30 条历史会话。其中 185 个决策点包含完整、可归档的
工具调用，适合进行成本分析。样本选择没有使用任务最终得分，也没有只挑选有利样本。

安全和工程检查全部通过：

- 相同输入重复运行得到相同结果：100%；
- 不读取决策点之后的未来信息：100%；
- 发送给模型的消息格式合法：100%；
- 当前目标和关键证据保留：100%；
- 被移出的内容可以从归档恢复：100%；
- 政策、确认和副作用回执错误删除数：0；
- 实验期间外部模型调用数：0。

但成本结果不理想：185 个合格决策点中只有 4 个真正降低了完整输入，逐决策点比较后的 token 差
中位数为 0。预先规定的门槛要求中位数严格小于 0，因此 F5-G1 被判定为 No-Go，后续的
GDSC-Structured 和外部模型试验均停止。

### 3.3 Phase 5.1：不用大模型，尝试从结构化字段中识别更多关系

在 Phase 5 之后，我们进一步检查了一个方向：能否在运行时记录“已消费、已替代、已失效”等关系，
并且通过结构化字段或正则匹配完成，不额外调用大模型。

为避免为了得到好结果而放宽安全要求，Phase 5.1 在实验前把证据分成两级：

- **Grade A，安全下界**：只有整个工具结果就是一个单一值，而且该值按相同数据类型和内容被后续
  工具参数使用时，才能认为它已经被完整消费。例如，查询只返回一个用户编号，后续查询明确使用了
  同一个编号。
- **Grade B，乐观上限**：如果一个复杂结果中的实体编号被后续使用，或者一个写操作可能使旧查询
  失效，则暂时假设旧记录可以删除。但由于缺少完整影响范围和版本信息，这一级只能用于估算上限，
  不能实际发送给模型。

正则表达式只用于识别结构化名称，例如 `user_id`、`order_number` 和 `update_*`，不根据自由文本
中的“已经完成”“已经取消”等词语直接判断记录失效。

结果如下：

| 条件 | 185 个合格决策点中输入减少的数量 | 配对 token 差中位数 |
| --- | ---: | ---: |
| Phase 5 原方法 | 4 | 0 |
| Grade A 安全规则 | 10 | 0 |
| Grade B 乐观上限 | 36 | 0 |

由于共有 185 个合格决策点，要使配对差的中位数严格小于 0，至少需要其中 93 个真正减少输入。
即使乐观上限也只有 36 个，因此 Phase 5.1 的 P51-G0 门禁判定为
`stop_old_corpus_path`，即停止继续开发旧语料上的规则。

## 四、目前真正的卡点是什么

### 4.1 不是单纯“算法太谨慎”

现有方法确实保守，但实验已经计算了一个偏激进的乐观上限。即使暂时把所有精确实体重合都当成可以
删除，覆盖面仍不足以改变多数决策点。因此，仅仅降低安全标准不能解决主要问题。

### 4.2 历史轨迹缺少生命周期证据

现有工具记录通常只包含调用参数和返回结果，没有明确说明：

- 这个操作影响了哪个实体；
- 修改前后的实体版本是什么；
- 哪些旧查询结果已经失效；
- 哪条结果已经被哪个后续操作完整消费；
- 不可逆操作对应哪个可验证回执；
- 后续查询是否完整覆盖了旧查询提供的信息。

缺少这些字段时，系统只能从文本或重复出现的编号中猜测。猜测可以增加删除量，但无法满足论文需要的
安全证据。

### 4.3 固定成本占比较高

模型输入不仅包含可删除的工具历史，还必须包含系统政策、工具定义和消息协议等固定内容。即使删除一部分
历史，完整请求的总 token 也可能没有明显变化。这也是 Phase 4 中理论上限低于 30% 的原因。

### 4.4 当前只有离线工程证据

目前可以证明的是系统可复现、协议正确、归档可恢复和已检查范围内没有关键误删。尚未证明：

- 外部模型实际输入费用稳定下降；
- 任务成功率不降低；
- 不会出现新的政策违规或不可逆错误；
- 在其他数据集和模型上仍然有效；
- 人工专家对 dead/live 标签具有足够一致性。

因为前置成本门禁没有通过，这些外部实验没有被启动，不能把“没有运行”描述成“效果相同”或“安全性
已经得到最终证明”。

## 五、当前成果是否有价值

虽然主要效果门禁没有通过，项目仍然形成了几项可复用成果：

1. 一套可以重放、归档和验证工具调用历史的 TraceGraph 基础设施；
2. 能够区分当前活动证据、已解决失败、被替代结果和副作用回执的生命周期表示；
3. 对最终完整模型请求进行计量和哈希绑定的方法，避免只计算局部文本而夸大节省；
4. 一个保守、可恢复、保持工具消息协议的删除式上下文管理器；
5. 一套 outcome-blind 的离线门禁流程和明确的负结果；
6. 关于失败原因的诊断：瓶颈主要来自观测字段不足和固定请求成本，而不只是剪枝策略不够激进。

这些成果支持工程方法和研究边界方面的结论，但目前不足以支持“该算法显著降低大模型工具调用成本”
这一主要效果主张。

## 六、需要导师决定的问题

### 方案 A：在当前结论处封存项目

将 Phase 4、Phase 5 和 Phase 5.1 作为完整的负结果与工程诊断保存，不再投入新的数据采集。优点是
研究边界清晰，不会因事后修改指标而损害可信度；缺点是无法形成原计划中的正向算法效果结论。

### 方案 B：另立“运行时生命周期遥测”研究

不再从旧文本中猜测关系，而是在工具执行时直接记录：

- `entity_key`：操作针对的实体；
- `entity_version_before/after`：修改前后版本；
- `effect_scope`：操作改变了哪些字段或对象；
- `receipt_id`：不可逆操作的回执；
- `consumes_event_ids`：完整消费了哪些旧结果；
- `invalidates_event_ids`：确定性使哪些旧结果失效。

这个方案与现有结果逻辑一致，但它是新的数据生产条件，必须重新预注册、修改工具环境并采集新轨迹。
Phase 5.1 的门禁失败后，当前计划没有自动授权这项工作。

### 方案 C：调整论文问题

把论文重点从“已经证明能够稳定节省 token”调整为：工具调用上下文压缩的安全边界、完整请求成本
计量、可恢复剪枝框架，以及为什么仅靠事后轨迹难以识别生命周期关系。这样可以保留现有工程和负结果，
但论文定位、对照实验和贡献表述需要重新设计，不能沿用原来的效果主张。

## 七、建议的当前处理

在导师做出方向选择前，建议先封存现有状态：

1. 生成 Phase 5.1 完成态的最终 checkpoint；
2. 选择性提交并推送代码、配置、测试和文档；
3. 单独备份所有实验 artifacts，因为其中很多文件不由 Git 跟踪；
4. 保存逐文件 SHA-256、运行环境、测试日志和恢复说明；
5. 保持 Phase 4 的 30% 历史门槛、R2/E0 No-Go、F5-G1 No-Go 和 P51-G0 Stop 不变。
