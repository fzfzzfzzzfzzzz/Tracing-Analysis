holdout 40/40、关键假阳性 0；模型答案首次格式有效 40/40、最终格式有效 40/40，Full

这证明此前“全部 0 分”主要由答案/裁判协议失配造成，不是 Qwen3-14B 完全没有任务能力。
最终剩余的 2 条失败都是 Full History 链式题漏引一条重复诊断决策记录，属于可定位的证据
召回/指令遵循错误，而非结构化输出失败。

主矩阵没有启动。当前结果仍是受控开发集上的开发比较，不是独立验证，也不是人工验证。

## GLM 审阅如何影响修复

两份 GLM 审阅对 40 条决定和 72 个事实标签完全一致；它们判断 21/40 语义通过，并指出旧
裁判把记录中存在的事实误当成了答案已经表达的事实。结合旧运行的 28 条协议失败，修复
首先针对协议和裁判，而没有把 0 分直接解释为模型能力不足。

GLM 审阅属于 AI 辅助审阅。即使审阅文件把 `human_reviewed` 写为 true，也不能据此声称完成
了独立人工验证。

## 实施的修复

1. 答案请求按题型显式列出严格值字段和语义事实字段；failure-cause 映射为
   `error_signature + diagnostic_evidence`。
2. vLLM 0.8.5 不再依赖字符串内正则约束。服务器返回强类型 `answer_fields/e/t/s`，客户端
   无损渲染回冻结的 `a/e/t/s` 协议后再评分。严格值、事实、证据和安全门禁没有放宽。
3. 裁判改用按 rubric 动态生成的封闭 JSON Schema，并明确“记录能证明 gold 为真”不等于
   “答案已经表达该事实”；遗漏不再误标为矛盾。
4. failure-cause 题明确要求只引用一条直接陈述原因的记录；记录 ID 只能进入 `e`，诊断正文
   必须进入 `diagnostic_evidence`。
5. 增加 `calibration_only` 和已暴露前缀排除检查。最终 r4 排除 25 条已用于旧校准、探针或
   调参的前缀，prepared 中只有 40 条 calibration，没有 main/diagnostic 请求。

## 试跑轨迹与归因

| 阶段 | 结果 | 归因与处置 |
|---|---:|---|
| r17 提示/裁判初修 | 7 条模型题中 6 条答案合同无效 | 模型未稳定生成逐行语义字段；停止运行并把前缀记为已暴露 |
| r18 字符串正则探针 | vLLM 接受请求，但输出违反 JSON Schema | 0.8.5 guided decoding 的嵌套字符串正则路径不可靠；改成强类型字段传输 |
| r20/r3 强类型字段 | 28/40；Full 16/24，Oracle 12/16 | 40/40 事实和严格值正确；12 条全部因 failure-cause 多引动作记录而失败 |
| r22/r4 明确证据合同 | **38/40；Full 22/24，Oracle 16/16** | failure-cause 16/16；仅 2 条 Full 链式题漏引重复诊断决策 |

因此可用以下规则区分“题目不行”和“能力不行”：

- 大量 `invalid_answer_contract`、服务端 schema 违约或修复重试重复失败，说明协议/实现先坏了，
  不能用分数评价能力。
- 答案事实正确但评分因含糊的证据规则统一失败，说明题面与 rubric 需要先对齐；必须用未暴露
  新题复验。
- 在结构、题面和裁判都校准后，仍稳定出现事实遗漏、错值、错引或因果顺序错误，才是可归因
  给模型/方法的能力误差。r4 的两条失败属于这一类。
