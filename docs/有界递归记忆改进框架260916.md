# 有界递归记忆改进框架（260916）

## 定位

当前实现是 **bounded recursive memory improvement**：Agent 从失败轨迹中形成外部经验，经验证后更新版本化记忆，再在后续任务中评估行为变化。

它不是模型权重级 RSI，也不允许 Agent 自行修改验证规则、工具权限或正式测试集。论文中应称为“经验驱动的递归记忆改进”或“有界自我改进循环”，除非后续确实加入并验证更强的自修改机制。

## 循环

代码入口为 `tracegraph.benchmark.recursive_memory.BoundedRecursiveMemoryLoop`：

```text
公开执行轨迹
  → ExperienceExtractor
  → FailureExperience
  → MemoryUpdateGenerator
  → MemoryUpdateCandidate
  → UpdateValidator
  → ValidationEvidence
  → 冻结 EvolutionPolicy 决策
  → 新 MemoryRevision 或拒绝
  → 固定检查点配对执行
  → PostCommitGuard
  → 保留或生成可审计 rollback revision
```

Extractor、Generator、Validator 和执行器均为注入接口。框架本身不调用模型，也不把人工 gold 伪装成在线抽取器。

## 数据对象

### FailureExperience

保存：

- 来源任务、检查点、prefix hash 和 split；
- 失败签名与稳定 action key；
- 原因、诊断、修复步骤和成功 action key；
- 适用条件、原始证据 ID；
- extractor 身份和估计 token 成本。

内容决定 `experience_id`。任何字段变化都会改变 ID。

`experience_from_failure_episode()` 可以将人工 `failure_episode_gold_v1` 转换为该结构，仅用于受控实验、评测或 fixture。生产抽取器必须实现 `ExperienceExtractor`，且不得访问隐藏 gold。

### MemoryUpdateCandidate

支持：

- `add`：增加经验；
- `replace`：用新经验替换旧条目；
- `retire`：停用过时或错误条目。

候选必须绑定父 revision、round、来源经验和 generator。新增或替换条目必须确实来自候选声明的经验，不能把未验证内容夹带进记忆。

### ValidationEvidence

验证分为独立布尔门禁：

- provenance；
- replay；
- regression；
- contradiction；
- safety；
- 是否观察了隐藏评测信息。

验证失败不会被自动修复。决策保存验证摘要，载入 ledger 时会重新核对，防止验证记录被事后修改。

### MemoryRevision

每个 revision 不可变，内容寻址并保留：

- parent revision；
- round；
- 完整 memory entries；
- 接受的 candidate IDs；
- update／rollback 类型；
- rollback 目标与原因。

多个候选以单个 batch 原子提交。若条目数或 token 上限超出，整个 batch 失败，不产生半提交 revision。

## 默认安全边界

`EvolutionPolicy` 默认只允许：

- dev 经验；
- dev 验证；
- 最多 8 个更新/轮；
- 最多 256 个 memory entries；
- 最多 32768 个估算 memory tokens。

test split 永远不能授权记忆更新。若未来使用 validation 做最终门禁，必须显式改变 policy，并保持 test 不可见。

候选或验证一旦声明观察了 hidden evaluation，更新会被拒绝。

## 提交后回滚

预提交 replay 通过并不保证新记忆在真实继续执行中一定有效。因此框架提供第二道 `PostCommitGuard`：

- 最小配对任务数；
- 成功率不得低于阈值；
- 重复失败率不得恶化；
- 可选 token 和 latency 上限。

若固定检查点比较未通过，框架不会删除新 revision，而是创建一个新的 rollback revision，恢复父 revision 的条目并保留完整审计链。

## 纵向指标

`compare_revisions()` 以 `(task_id, checkpoint_id)` 为严格配对单位，报告：

- success-rate delta；
- repeated-failure-rate delta；
- reacquisition、tool call、token 和 latency delta。

`summarize_recursive_improvement()` 汇总多轮版本增长、接受/拒绝、回滚以及平均行为变化。输出明确标记为外部记忆改进，不能直接解释为权重级 RSI。

## 持久化

`write_ledger_snapshot()` 写入内容寻址、不可覆盖的 JSON 快照；`load_ledger_snapshot()` 会验证：

- 快照整体 digest；
- experience、candidate、decision 和 revision 的内容 ID；
- validation 与 decision 中保存的摘要；
- revision 父链和当前 head。

## 已实现的首组插件

`tracegraph.benchmark.recursive_memory_plugins` 提供第一组不依赖模型的保守实现：

### DeterministicRecoveryExtractor

只抽取公开轨迹中能够直接观察到的：

```text
失败调用 → error → 一个或多个显式 decision → 同目标重试 → success
```

它不读取 query 或 gold。失败/成功 action 使用稳定 key；共享的非动作参数作为适用条件；全部原始事件 ID 保留在 provenance 中。当前故意不猜测跨多步调查、隐式 decision 或非邻接恢复。

### ConservativeAddOnlyGenerator

只为父 revision 中尚未出现的 failure scope 生成 `add`：

- 同一 scope 的重复经验自动去重；
- 同一 scope 出现互相矛盾的恢复建议时不生成候选；
- 不自动 replace 或 retire；
- 每轮候选数量受独立上限限制。

### DeterministicMemoryRenderer

把完整 FailureExperience 渲染成 Agent 可消费的记录，并按查询相关性在预算内选择。单条经验要么完整进入，要么完全省略，不允许切断 failure reason、diagnosis、recovery steps 或 provenance。

### CheckpointReplayValidator

接受同一 `(task_id, checkpoint_id)` 上的 baseline 与 evolved 继续执行结果，复用 `PostCommitGuard` 计算成功率、重复失败、重新获取、调用、token 和时延变化，并生成正式 `ValidationEvidence`。

`continuation_trial_from_mini_run()` 可以直接读取已完成的 `server_eval.mini` 分支产物，检查 tool attempt/result 是否闭合、provider usage 是否有效，并转换为统一 continuation trial。它只读取已经完成的运行，不会自动启动 Docker 或模型。

`MiniArtifactReplayProvider` 进一步把 baseline/evolved 两个已完成分支绑定到候选更新。读取时会强制检查：

- 两条分支来自同一个内容校验通过的 checkpoint；
- task、plan、model、method 和总预算相同；
- 两条分支预留相同的 revision-memory 子预算；
- baseline 使用父 revision；
- evolved 使用该候选的确定性 preview revision；
- 两条分支都记录了内容寻址的 memory source。

因此，不能把任意两个结果目录拼成“配对回放证据”。

### MiniModel revision-memory 接入

`MiniModel` 已支持在总历史预算中预留独立的 failure-experience memory 子预算。`mini-run` 可用：

- `--memory-ledger`：运行已提交 ledger 的当前 revision；
- `--memory-revision`：运行一个独立 revision 快照，主要用于提交前候选回放；
- `--memory-budget`：从相同总预算中预留给 revision memory 的额度。

`preview_candidate_revision()` 只物化候选，不写入 ledger；`write_revision_snapshot()` 将父 revision 或 preview revision 写成内容寻址快照。公平比较时 baseline 也必须传入父 revision 快照并预留相同子预算，不能让 baseline 独占完整历史预算。

### 冻结 replay plan

`tracegraph.benchmark.recursive_memory_replay` 已实现离线计划层：

- `prepare_mini_replay_plan()` 冻结 prepared mini plan、calibration、checkpoint、候选、父 revision、候选 preview、模型/方法/预算和两个新输出位置；
- `load_mini_replay_plan()` 重验 plan digest、全部输入文件哈希、checkpoint digest 和两份 revision 的内容身份；
- `execute_mini_replay_branch()` 每次只运行一个明确指定的 baseline 或 evolved 分支，并继续要求 `execute=True`；
- `mini_replay_pair_from_plan()` 只在两个结果目录都存在后，将它们绑定回 `MiniArtifactReplayProvider`。

生成 replay plan 不会调用模型或启动容器。baseline/evolved 不会被一个隐式循环自动连续运行，方便在每次真实执行前保留人工成本和运行环境检查点。

## 尚未实现

框架接口和状态机已经具备，但以下组件仍需要后续实现和实验选择：

1. 超出邻接同目标重试模式的多阶段 deterministic extractor；
2. 经过约束的模型驱动 memory/skill generator；
3. 多任务 curriculum、跨轮调度和批量 replay 编排；
4. 正式 validation 阈值与统计方案。

下一步是在一个公开开发任务上，人工逐次启动冻结 plan 的两条隔离分支，跑通一次真实闭环并据此冻结 validation 阈值。完成这一步后，才考虑多任务调度或模型生成的技能更新。
