# Qwen3-14B：BM25 与 TraceGraph 0.4 多预算效率前沿（260914）

## 结论

这轮已经回答了 `pro建议260912.md` 要求的关键归因问题：当前 TraceGraph 0.4 在低预算下会拆断完整失败链，平面 BM25 不会；到 1024 token 档，TraceGraph 才在本开发切片上恢复到与 BM25 相同的正确率，并使用更少的实际上下文和模型输入。

但这还不能写成“图结构优于 BM25”。BM25 在四个预算档都是 24/24；TraceGraph 在 512、768 都只有 16/24，在 1024、1536 才是 24/24。当前最准确的说法是：**TraceGraph 存在一个由链选择/打包造成的低预算失效区；修复后是否能在 512/768 同时保持完整链和更低成本，才是下一轮要验证的算法增益。**

## 冻结设计与完整性

- 模型固定为 `Qwen3-14B-rev-40c0698`，BF16、TP=2、non-thinking、32K context，只使用服务器 GPU 0/1。
- 固定 8 个已暴露的长开发前缀；failure family 各 4 个，R0–R3 各 2 个。
- 固定方法为 `flat_bm25_archive` 与 `tracegraph_0_4`，预算为 512、768、1024、1536。
- 每个预算、每个方法 24 个主项（8 前缀 × 3 问题类型），合计 192 个主项；无事后剔除。
- 每个选中预算的模型校准均为 40/40；full history 24/24，oracle 16/16。裁判门禁分别为 38/40、38/40、40/40，critical false positive 均为 0。
- 结果仅是 development-only；前缀和协议均已参与开发，不能当作独立验证。

## 主结果

| 预算 | BM25 hard/audit | TraceGraph hard/audit | BM25 完整链 | TraceGraph 完整链 | BM25 平均上下文 | TraceGraph 平均上下文 | TraceGraph 输入节省 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 512 | 24/24 | 16/24 | 8/8 | 0/8 | 359.12 | 235.79 | 12.89% |
| 768 | 24/24 | 16/24 | 8/8 | 0/8 | 680.88 | 283.96 | 31.05% |
| 1024 | 24/24 | 24/24 | 8/8 | 8/8 | 680.88 | 326.12 | 27.75% |
| 1536 | 24/24 | 24/24 | 8/8 | 8/8 | 1002.62 | 638.62 | 22.75% |

低预算的 8 个 hard-pass 差异全部是同一批完整链题：TraceGraph 相对 BM25 为 0 win / 8 loss / 16 tie；未校正的配对精确符号检验 p=0.0078125。样本仅 8 个前缀，这个数用于确认失败定位，不用于正式显著性主张。

失败原因不是“题目不行”或“Qwen3-14B 没能力”：

- 同一个模型、同一道题、同一预算下，BM25 全部通过。
- failure-cause 与 current-state 两类题，TraceGraph 在所有预算也全部通过。
- 512 档的 8 条 TraceGraph 链上下文都包含失败调用 E002、错误 E003、替代调用 E006、成功结果 E007，却统一漏掉诊断决定 E004 和切换决定 E005。
- 768 档有 7 条漏 E004；剩余 1 条上下文含完整链，但回答多引了当前状态 E023，仍未通过严格链。
- 到 1024 后，同一模型的 8 条链全部可见、按序引用并通过。

尤其重要的是，512/768 的 TraceGraph 上下文实际平均只用了 235.79/283.96 token，并未接近预算上限；BM25 在 512 档用 359.12 token 就能容纳并答对完整链。因此问题是链选择和证据单元打包，不是物理预算装不下。

## 效率前沿

在质量相同时，TraceGraph 确实更省：

- 1024 同档：两者均 24/24；TraceGraph 平均上下文少 52.10%，实际 answer prompt 输入少 27.75%（22,163 对 30,677）。
- 1536 同档：两者均 24/24；TraceGraph 平均上下文少 36.30%，answer prompt 输入少 22.75%（29,663 对 38,399）。
- 跨预算最省的满分点：TraceGraph-1024 与 BM25-512 都是 24/24；前者平均上下文仍少 9.19%（326.12 对 359.12），answer prompt 输入少 3.45%（22,163 对 22,955）。

这说明图方法具备压低实际输入的潜力，但现实现版本要付出更高的名义预算才能避免漏链。没有修复低预算断链前，不能声称它支配 BM25 前沿。

## 中断与恢复审计

原 r2 运行在 768 诊断阶段遇到一个 `irrelevant` 格式修复请求超时。请求已经发送但未返回可验证 usage，append-only 账本按设计以 `provider outcome or usage uncertain; stopped without retry` 停止；没有删除、重写或重放该请求。

在未查看主方法胜负前，恢复方案被写入预注册：r2 只取已完整的 512/768 主项；1024 和 1536 使用独立单预算分片补齐。1024 在完整主项后额外跑了 8 条诊断并于 200-job 边界暂停；1536 在 192-job 主边界暂停。合并规则固定后才统一解盲。

服务器产物与本地下载的 SHA-256 完全一致。实验结束后 vLLM 已停止，GPU 0/1 均为 10 MiB、0% 利用率。

## 根据 pro260912 的下一步

下一步不是把默认预算直接抬到 1024，也不是立刻扩大模型矩阵。应先定点修复 `pro建议260912.md` 第 202–204 行指出的问题：

1. 把 E002–E007 的失败到成功链作为不可拆分的证据单元选择，而不是逐事件贪心加入。
2. 若完整原始链确实无法放入预算，则保留含诊断决定和切换决定的紧凑链摘要，同时携带原始事件指针；本切片的 512 档实际上能放下完整链，优先修复选择逻辑。
3. 对严格链题禁止用无关 current 记录挤占或污染链证据；保持当前状态题的独立分支。
4. 用同一冻结 8 前缀做开发回归，成功条件预先定为：TraceGraph 在 512 与 768 均达到 24/24、链 8/8，且实际 answer 输入不高于同档 BM25。
5. 达标后再接入官方 ACON、AMA-Agent 和滚动摘要，并在未参与本轮修复的新真实轨迹/独立测试集上验证；否则本轮仍只能证明开发集上的定点修复。
