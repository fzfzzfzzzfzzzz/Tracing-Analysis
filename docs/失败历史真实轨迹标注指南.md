# compression_audit_v1 真实轨迹标注指南

## 原则

候选挖掘程序只能减少人工浏览量，不能产生 benchmark gold。一个窗口中出现 `error`、重复观察或最终任务成功，都不足以自动证明完整的“失败 → 诊断 → 切换 → 成功”因果链。

每条最终样本必须由两名标注者独立完成，再由仲裁者产生第三份 `adjudicated.jsonl`。标注者在独立阶段不能看到对方答案。仲裁文件必须保存两份输入行的 SHA-256；程序会重算并核对。

## 1. 从固定版本提出候选

先把固定 revision 的官方数据导出为 JSON、JSONL 或 Parquet。本程序不自动下载，也不把网络上的浮动 `main` 当作数据版本。

```powershell
$env:PYTHONPATH = "src"
python scripts/mine_compression_audit_candidates.py `
  --config configs/compression_audit_v1.json `
  --swe-source path\to\openhands-trajectories.parquet `
  --ama-source path\to\ama-bench.json `
  --output data\compression_audit\real_annotations_v1
```

输出的 `candidates.jsonl` 保存源文件 SHA-256、固定 revision、原记录 SHA-256、规范化事件和启发式窗口。每行仍是 `annotation_status=candidate`，失败链字段为空，`gold_created=false`。对 Parquet 的读取需要项目的 `analysis` 可选依赖。

Parquet 通过 Arrow 直接读成 Python 嵌套列表，避免消息与工具调用被 NumPy 数组转换丢失。安装命令为 `python -m pip install -e ".[analysis]"`。

候选池应多于最终 60/40 配额。任何缺少原始事件、无法判断切换原因、成功证据不明确，或需要猜测隐藏状态的候选都应拒绝，不能为了凑数降级标准。

## 2. 选择与 split

最终选择 60 条 SWE-Gym/OpenHands 和 40 条 AMA-Bench：

- SWE 条目必须能在固定 Docker 快照中回放，且验证命令可重复执行；它进入 Audit-QA 和 Interactive-Reacquisition。
- AMA 条目只进入 Audit-QA，不要求 Docker 回放。
- 先按源仓库分组，再把整个仓库分给 dev、validation 或 test；同一任务也不能跨 split。
- 最终数量严格为 dev 20、validation 20、test 60。

如果合法的完整链不足 100 条，或可回放 SWE 链不足 60 条，停止 `v1.0` 发布。

每条 SWE 的 `replay.verification` 必须包含 `status=passed`、`exit_code=0`、带 `@sha256:` 的固定 `image_ref`、命令参数数组 `command`、标注目录内的 `log_path` 和匹配文件内容的 `log_sha256`。`snapshot_ref` 也必须非空。仅勾选 `docker_replayable=true` 不会通过门禁；构建器会复制并校验回放日志。

## 3. 标注字段

保留候选行的 `source`、`candidate_id`、`repository`、`task_id`、`trajectory_revision` 和 `prefix.events`。不要修改来源事件的内容或 ID。

在 `failure_chain` 中填写：

- `failure_family`：失败类别；
- `failed_action` / `failed_arguments`：实际失败的方法及调用参数；
- `error_signature`：稳定、最小的机器可比错误签名；
- `diagnostic_evidence`：记录里支持失败原因的说明；
- `switch_decision`：为什么停止原方法并切换；
- `replacement_action` / `replacement_arguments`：替代方法及参数；
- `resolution_evidence`：证明替代方法成功的观察；
- `ordered_source_event_ids`：按时间排序的必要来源事件，至少五个、不得重复；
- `recoverability`：R0、R1、R2 或 R3。

每个规范化事件的 `causal_role` 可标成 `failed_action`、`failure_result`、`diagnostic_evidence`、`switch_decision`、`replacement_action` 或 `resolution_evidence`。如果一个来源事件同时支持多个字段，使用 `evidence_source_event_ids_by_field` 明确列出各字段证据；不要复制或伪造来源事件。

R3 表示重复失败动作可能产生副作用或不可重复。它的 `replay.docker_replayable` 不能被理解为允许在正式运行中执行原副作用；正式 harness 仍只模拟并阻断。

## 4. 独立标注与仲裁

两份独立文件分别写入 `annotator_a.jsonl` 和 `annotator_b.jsonl`，使用不同且非空的 `annotator` 标识，状态写作 `annotated`。仲裁者逐条解决类别、字段值和证据事件分歧，输出 `annotation_status=adjudicated`，填写非空 `adjudicator`、`annotator_a_sha256` 和 `annotator_b_sha256`。

仲裁前门槛为：

- `failure_family` 和 `recoverability` 等类别字段的最小 Cohen's κ 不低于 0.80；
- 两份标注所选证据事件集合的平均 F1 不低于 0.90。

仲裁后，关键字段、证据引用、来源 revision、Docker 回放信息和 split 必须 100% 完整。程序还检查候选来源、双人身份、输入行哈希、配额、任务/仓库泄漏和事件 ID 有效性。

如果某类别字段在整个标注集里只有一个常量类别，κ 无法估计，不会被记成 1.0。事件因果角色只留在组织者标注及 gold 中，公开 prefix 会移除这些标签。

## 5. 构建与门禁

完成标注后重新执行 `benchmark-build`。构建器把标注输入复制进新数据目录，核对配置中固定的 source revision，并在门禁通过时生成真实 public prefix/query 和隐藏 gold。

```powershell
python -m tracegraph benchmark-validate `
  --dataset outputs/compression_audit/my_v1_build `
  --require-v1
```

若命令退出非零，应按报告修正来源或标注；不得手工把 `v1_ready` 改成真。
