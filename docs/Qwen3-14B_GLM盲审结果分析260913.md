# Qwen3-14B GLM 盲审结果分析（260913）

## 结论

GLM 的两份重复盲审给出了完全一致的事实标签和语义通过结论。按这组标签，Qwen3-14B 的真实答案语义通过率为 21/40（52.5%），holdout 为 9/20（45%）。失败高度集中在 `audit_chain`：16/16 全部失败；`distractor_current` 为 8/8，`audit_failure_cause` 为 13/16。

这不是“题目都不可答”。40 条输入中的 72 个必要事实全部能在提供给模型的 records 中逐字找到，40/40 答案的必要 evidence ID 也全部引用成功。更符合证据的解释是：模型完成了检索和引用，但在 `answer.a` 中系统性漏写了已找到的诊断细节或成功结果；同时旧裁判又把 72/72 个事实全部标成 `supported`，没有识别任何遗漏。

当前不能启动主矩阵。按 GLM 标签计算，真实答案裁判 holdout 门禁为：协议有效 6/20（要求至少 19）、语义结论正确 3/20（要求至少 18）、critical false positive 0（要求 0）。前两项严重失败。

两份文件均覆盖 40/40 条，blind ID 无重复，schema 和事实键完整。A/B 在 40/40 个语义结论、72/72 个事实标签和 40/40 个 contradictions 列表上完全一致；40 条说明文字均不同。标签合计为 `supported=45`、`missing=27`，没有 `contradicted` 或 `uncertain`，没有引用任何矛盾原文。

但是，reviewer ID 是 `reviewer-a-ai-assisted` 和 `reviewer-b-ai-assisted`，且用户明确说明审阅由 GLM 完成。因此，即使文件中写了 `human_reviewed=true`，本分析也不把它认定为两位独立人工审阅，不设置 `human_validated=true`，也不据此给主矩阵放行。两次同模型审阅可作为稳定性较好的开发期标签，但误差高度相关，不能替代独立人工或不同裁判来源。

## 旧硬分与 GLM 语义标签的差异

旧 hard pass 为 36/40，但只与 GLM 语义通过同时成立 18 条；另有 18 条 hard pass 被 GLM 判为语义失败。按题型：

- `audit_chain`：hard pass 15/16，GLM 语义通过 0/16；
- `audit_failure_cause`：两边都是 13/16，但具体案例并非完全相同；
- `distractor_current`：两边都是 8/8。

所以 hard pass 主要证明结构、引用和严格字段匹配，不足以替代答案文本的语义完整性判断。原先看到 0/48 或接近全零的 audit 分，也不能反向推出“题目不行”；多个评分层在测不同性质。

## 裁判故障

旧裁判对全部 72 个事实都输出了 `supported`。与 GLM 标签相比：45 个一致，27 个本应是 `missing`。裁判协议仅 12/40 有效；错误为：

- `contradiction_not_exact_answer_substring`：19；
- `unknown_extraction_field`：8；
- `extraction_span_mismatch`：1。

28 条协议失败中，GLM 判 10 条答案语义通过、18 条失败。也就是说，协议失败不是模型能力失败的同义词：它同时遮蔽了正确答案和不完整答案。

在 12 条协议有效案例中，裁判语义结论只与 GLM 一致 8 条（66.7%）；4 条是 false negative。唯一“协议有效且 GLM 判失败”的答案中，裁判虽然也给出总体失败，但仍错误地把缺失事实标成了 supported，因此理由不可信。holdout 的具体门禁为：

| 指标 | 实际 | 要求 | 结果 |
|---|---:|---:|---|
| holdout 数量 | 20 | 20 | 满足 |
| 协议有效 | 6 | ≥19 | 失败 |
| 语义结论正确 | 3 | ≥18 | 失败 |
| critical false positive | 0 | 0 | 满足 |

`critical false positive=0` 不能单独说明裁判可靠，因为大多数输出已经在协议层失效，且有效样本中存在 false negative。

## 题目、模型、方法与裁判的归因

当前证据支持以下优先级：

1. **裁判协议/裁判能力问题：确定存在。** 协议有效率太低，并且事实标签退化为全部 supported。
2. **答案生成完整性问题：确定存在。** 证据引用 40/40 成功，但链式回答 0/16 明确写全必要事实。
3. **题目不可答：没有证据支持。** 72/72 必要事实均逐字存在于可见记录中，三类问题的表现又有明显分化。
4. **记忆方法能力：目前不能下结论。** Full History 与 Oracle 在链式题上同为 0/8，说明共同的输出提示/回答格式是更靠前的瓶颈；需先修复后再比较压缩方法。

有一个设计限定需要保留：当前盲审标准要求事实必须由 `answer.a` 明确表达，只有 evidence ID 不算支持。如果研究定义允许读者沿 evidence ID 回看记录并补全答案，那么这些结果会变宽松；但那将是更改评价目标，不能与当前协议结果混用。

## 下一步

1. 只用 tuning 20 条，将真实遗漏案例加入裁判校准：允许 `missing`，禁止把未出现在答案中的 gold fact 放入 contradictions，限制 extraction 字段与精确 span。
2. 修改回答提示，要求 `answer.a` 对链式问题逐项明确写出失败原因、切换决定和已观察到的成功结果；错误签名、action 名和 evidence ID 不能代替自然语言事实。
3. 先重跑小型 Full History/Oracle 校准，而不是主矩阵。验收重点是 `audit_chain` 不再 0/16，以及裁判真实答案 holdout 达到 19/20 协议有效、18/20 正确、0 critical false positive。
4. 因为本次分析已经查看了当前 holdout 的聚合和案例模式，如果依据这些结果调参，当前 holdout 不再是严格未见的确认集。正式放行前应换一组 prefix-disjoint 的新 holdout。
5. GLM 标签保留为 `development_only`、`independent_validation=false`。若最终报告需要人工验证声明，仍需真实人工复核，或至少引入不同模型/不同提示的独立仲裁并如实标注为 AI 审阅。
